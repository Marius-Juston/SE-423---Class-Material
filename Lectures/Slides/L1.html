6. The Class - The “Red Board”

  • What are you going to be doing with the Red Board?
  • Playing with LEDs, push buttons, light sensors, RC servo, microphone, IMU
  • Texas Instruments Digital Signal Processor (DSP) running at 150 MHz
    • Arduino at 20–40 MHz
  • 16-bit and 32-bit integers, only
  • Floating-point capabilities
  • You get to keep it for future mechatronic projects!
Lecture notes

This slide introduces the Red Board, the hardware you use all semester. The photo on the right shows a red Texas Instruments C2000 LaunchPad, the TMS320F28379D, plugged into the larger green custom breakout board from the previous slide, version 5.0. The green board carries a grid of 16 small LEDs, four push buttons, a buzzer, a photoresistor light sensor, DRV8874 motor driver circuits, trimpots, and DAC and ADC test points for the oscilloscope. It also has header areas labeled for an ESP32 DevKit, an Orange Pi Lite, SPI devices and a W5500 Ethernet module.

The bullets list what you do with it: LEDs, push buttons, light sensors, an RC servo, a microphone and an IMU, which is an inertial measurement unit that measures acceleration and rotation rate. Each one is a small lab that teaches a peripheral, such as GPIO, PWM, ADC or SPI.

The processor is a TI Digital Signal Processor running at 150 MHz, compared with roughly 20 to 40 MHz for a typical Arduino. That speed lets you run filters and feedback control loops at high sample rates.

"16-bit and 32-bit integers, only" means the chip has no 8-bit data type. On this family even a char is 16 bits wide. This catches students who copy Arduino code that assumes 8-bit bytes. The chip also has hardware floating-point support, so you can write control math with floats without a large speed penalty.

You keep the board after the course for your own mechatronics projects. You program all of this in C, which is the topic of the next slides.

This slide follows up on the show of hands from the previous slide, "Who here knows how to program in C?", and lays out what the course expects from you in C. The title is "The Class – C Programming," and a blue hexagonal C language logo sits in the top right corner.

The main points: you program the embedded system, the Red Board, in the C programming language. C is not taught in this course, so you learn it on your own. The C you need is not complicated. Pointers appear only minimally, and you will not build data structures such as graphs, trees or linked lists. Most embedded code here is variables, if statements, loops, functions, arrays and reading and writing hardware registers.

Printing a variable's value is often the fastest way to find out why your code is not doing what you expect. Remember from the previous slide that the processor uses 16-bit and 32-bit integers, so make sure your format specifier matches the variable's type.

Lecture notes

This slide continues the course goals from the previous slide and has no figures, only bullet text. It opens with "We have a long way to go!" and then asks whether all these things scare you a bit. If so, that is good, because you will learn a lot of material by the end of the semester.

The main point is the style of the course: it does not sit and teach theory. The slide gives two examples of what is not covered. The first is why a PI controller is stable. A PI controller is a proportional-integral controller, a feedback law that combines the current error with the accumulated error over time. The second is why the A* (A-star) algorithm is optimal; A* is a graph search method for finding shortest paths, which you will use for path planning. Those proofs belong to control and algorithms courses. Here the message is "let us implement this algorithm."

The emphasis is on implementation. The slide asks how you make sure an algorithm actually works on the circuit board, meaning real hardware with real timing, sensors and limits. Most of your code runs on the small processor on the board, which the slide says runs at 150 MHz, fast for an embedded system. That speed is generous, but every control loop still has to finish within its time slot, so how you write the code matters.

A common mistake is assuming that if the math is right, the robot will behave. Most of your debugging time goes into the gap between the equation and the hardware.

This slide, titled "The Class – AI Content," has five text points about starter code and the course policy on AI tools. There are no figures.

First, you never start from a blank C file. Every homework comes with its own starter code file, which is added to the course project and already contains the C code you need to build on. Your job is to fill in and extend that code, not to write everything from scratch.

// cpu_timer1_isr - CPU Timer1 ISR

__interrupt void cpu_timer1_isr(void)

CpuTimer1.InterruptCount++; // MJ: Increments the timer's internal interrupt counter

}

Lecture notes

This slide covers how you turn in code. You submit your commented code in Gradescope, and if your code is not commented, points are taken off. You compile the whole assignment into a single PDF, and you answer any other questions inside that same assignment document rather than separately.

The bottom half of the slide is an example of a properly commented function, shown in code formatting. A first comment line reads: cpu_timer1_isr, CPU Timer1 ISR. Next is the declaration: __interrupt void cpu_timer1_isr(void). The body has one statement, CpuTimer1.InterruptCount++; with the trailing comment "MJ: Increments the timer's internal interrupt counter."

ISR stands for interrupt service routine: a function the processor runs automatically when a hardware event occurs, here CPU Timer 1 expiring. The __interrupt keyword tells the TI compiler to treat the function as an ISR, so it saves and restores the processor state correctly. The single line just counts how many times the timer has fired. You write many of these timer ISRs on the Red Board.

Notice that the added comment begins with the initials MJ. That shows how to mark your own comments so the grader can tell them apart from comments that came with the starter code. Good comments explain what a line does and why, not just restate the code.

A quick check: if this timer fires every millisecond, what does InterruptCount equal after two seconds? The answer is 2000.

Your code only counts if it still exists at submission time, so next we look at git, which you use to back it up.

17. The Class – Git

  • You will be using a version control (think of it as a backup system) called “git”
  • For it to be effective, be sure that you are “committing” and “pushing often! If you do not, then you will most likely lose your data
  • You are sharing the machines with all the sections; it is HIGHLY probably someone will accidentally change your code. ( yes, it happens very often )
  • Any software related job uses it, so best to get started on good practices now!
Lecture notes

This slide, titled "The Class – Git," has four bullet points and, below them, the Git logo (an orange diamond with a branching line) beside the GitHub logo (the black octocat silhouette above the word GitHub). Together they show that you use git for version control, with GitHub hosting your repositories.

Version control is software that records the history of your files, so you can see what changed, when, and go back to an earlier working version. The slide calls it a backup system, which is a good starting picture. Two terms matter. A commit is a saved snapshot of your changes, stored on the machine you are working on. A push copies those commits up to the remote repository on GitHub. A commit that is never pushed exists only on that lab computer, so if the computer's copy is changed or wiped, your work is gone. That is why the slide says to commit and push often.

The third point explains why this matters so much here: you share the lab machines with every other section. It is highly probable that someone will accidentally edit or overwrite your project, and it happens very often. A good habit is to commit and push every time something works, and always before you leave the lab. When you sit down again, pull first so you start from your own latest code.

Finally, nearly every software-related job uses git, so building the habit now pays off well beyond this course. Your commented code from the previous slide lives in git, and the next slide covers when those submissions are due.

The previous slides covered the pieces of each lab: the checkoff, where you demonstrate your working code on the Red Board; the commented code you compile as a PDF and upload to Gradescope; and git, which keeps your work safe. This slide tells you when each piece is due. The days are fixed for the whole semester. The checkoff comes first, on Tuesday afternoon. Your code and written answers follow the next morning, on Wednesday. Use that gap to clean up your comments and finish the questions. Each lab ends on the Tuesday of the week the next lab begins, so the lab you are working on is wrapped up by the time the next one starts.

A common mistake is treating the Wednesday code deadline as the end of the lab. The checkoff has to be done by Tuesday at 5 PM, and it requires working hardware on a shared lab bench. Plan your time on the bench early, and commit and push your code often so it is ready when you demo.
