Lecture notes

This slide is a five-minute partner discussion that reviews last lecture and sets up today's topic, threads and processes. The slide says: talk to the person next to you and answer these two questions.

Question one: Timer 0 and Timer 1 run at the exact same time, in parallel, and both write the robot's position to the same array. Timer 0 writes (0, 1) and Timer 1 writes (1, 0). What is the worst possible case?

Question two: when driving a car, why is it safer and more robust to separate the "where should I be" calculations, called localization, from the "how much voltage goes to the steering motor" calculations, instead of using one single equation?

For question one, the worst case is not that one value wins. It is that the two writes interleave. Timer 0 writes x = 0, Timer 1 writes x = 1 and then y = 0, and Timer 0 finishes with y = 1. The array ends up holding (1, 1), and (0, 0) is also possible. That is a position neither timer ever computed. Any code that reads the array mid-update sees a mix of the two. This is called a race condition, and it gets a formal treatment later today. On a single-core processor, nested interrupts, where one interrupt pauses another, produce exactly this interleaving.

For question two, separating the jobs lets each run at its own rate: motor control is fast, while localization is often slower. Each block can be tested and debugged on its own, and you can swap sensors without touching the controller. A failure is also contained, so if localization drops out, the controller can still bring the car safely to a stop.

Lecture notes

This slide gives two definitions. A process is, informally, "a program in execution." A program is a set of CPU instructions plus the data needed for its task. In other words, it is essentially an executable file that sits in your file storage waiting to be run. The slide then adds that when you run the program, it needs more than that stored data, and the extra memory lives in the heap and the stack, which change size dynamically.

The key distinction is passive versus active. A program is a passive file on disk, like a recipe. A process is that recipe being cooked: it has been loaded into memory, it is executing, and it has state that changes over time.

The heap and stack are the new terms. The stack holds function call information: local variables, function arguments, and return addresses. It grows when a function is called and shrinks when it returns. The heap holds memory that the program requests while it runs, for example with malloc in C or new in C++. That memory stays allocated until it is explicitly freed. Neither region exists in the executable file. Both are created when the program starts running.

A common mistake is treating "program" and "process" as synonyms. One program can be run as several processes at the same time, and each process gets its own heap and stack.

13. Threads & Processes (9/22)

A thread is the smallest unit of a process.

A thread executes a sequence of operations for a process. Each threads maintains the same code, heap and data from the process; however, they have their own registers, program counter and stack.

Every process runs initially on a single-threaded way with the “main” thread.

However, it is possible to dynamically allocate the number of threads for your application to make it multi-thread.

Lecture notes

This slide is text only, under the title "Threads and Processes." It defines a thread and explains how threads relate to the process memory layout from the last two slides.

The first statement is that a thread is the smallest unit of a process: the smallest piece of work the operating system can schedule. A thread executes a sequence of operations on behalf of its process.

Recall the process layout of text, data, heap and stack. All threads in a process share the same code (the text region), the same global data, and the same heap. Each thread gets its own registers, its own program counter, and its own stack. The program counter is the register holding the address of the next instruction. Because each thread has its own program counter and registers, it can be at a different place in the code. Because each has its own stack, its local variables and function calls stay separate.

Every process starts single-threaded, running only the "main" thread, which begins at your main() function. Your program can then create additional threads at run time, which makes the application multi-threaded. On the Raspberry Pi, for example, one thread could read the LiDAR while another handles communication with the Red Board.

A common misconception is that threads are isolated like separate processes. They are not. Local variables live on each thread's own stack and are private. Globals and heap memory are shared, so two threads can read and write the same variable. That shared access is exactly what causes the race conditions you will see later in this lecture.

Quick check: if two threads call the same function, does each get its own copy of that function's local variables? (Yes, because each thread has its own stack.)

14. Threads & Processes (10/22)

Depending on your CPU and how many cores you have you will be able to parallelize how many threads can run at once.

A CPU with 4 cores allows you to run 4 threads in parallel, while a CPU with 8 cores allows you to run 8 in parallel.

What happens if you have more threads than cores, i.e., 1 core and wanting to use 8 threads?

Would we want to wait for one thread to finish before continuing another one? What happens if you must wait for a large file transfer to happen?

This is where scheduler works!

Essentially every thread is given a tiny bit of time to execute an instruction and then you cycle to the next thread, and you do this so fast it seems like you are running in parallel.

Lecture notes

This slide is text only, under the title Threads and Processes. It says that how many threads can run at once depends on your CPU and its number of cores. A 4-core CPU runs 4 threads in parallel, and an 8-core CPU runs 8. It then asks what happens when you have more threads than cores, for example 1 core and 8 threads. Should one thread finish before the next starts, and what if a thread is stuck waiting for a large file transfer? The answer is the scheduler. Each thread gets a tiny bit of time to execute, then the CPU cycles to the next thread, so fast that it looks parallel.

The previous slide showed that each thread has its own registers, program counter and stack. That is exactly what makes this switching possible. When the scheduler stops one thread, it saves that thread's registers and program counter and loads the next thread's. This is called a context switch. Each turn, or time slice, is short to a human, typically milliseconds, but long enough for the CPU to run many instructions.

Think about why running threads one after another is a bad idea. A thread waiting on a file transfer or a network packet does no useful work. With a scheduler, that blocked thread steps aside and another thread uses the CPU.

Keep two words separate. Concurrency means taking turns on shared cores. Parallelism means truly running at the same instant on separate cores.

Keep that distinction in mind for the next slide. There you apply it to the dual-core Red Board, where you only use CPU1, and to its timers and interrupts.

Lecture notes

This slide has no figures, just three lines of text on the standard title bar. The first line states that the Red Board, the TMS320F28379D, is a dual-core microcontroller, but we only use one core, CPU1. Then it asks two questions: how many threads can it run in parallel, and are the CPU timers and interrupts running truly in parallel?

On the last slide you saw that the number of threads that can truly run at once equals the number of cores, and that a scheduler fakes parallelism by switching between threads very quickly. Apply that here. CPU2 sits unused, so only one sequence of instructions executes at any instant: one thread in parallel.

What about your CPU Timer 0, 1 and 2 interrupts? They feel concurrent, but they are not truly parallel. Here is what actually happens. When a timer expires, the hardware raises an interrupt flag, and CPU1 pauses the main loop. It saves its registers, runs the interrupt service routine (ISR), restores the registers and resumes. Unless you explicitly enable nesting, one ISR also waits for another to finish. The interrupt controller decides which pending interrupt goes first by priority. So the interrupts take turns on a single core, much like a scheduler.

What is truly parallel is the peripheral hardware. The timer counters, ePWM, ADC conversions, eQEP encoder counting and SPI shifting all run on their own while the CPU does something else.

Why would we want multi-processes?

  • Fault Isolation and Robustness: Each process resides in its own isolated virtual address space. If a process experiences an error, it typically cannot corrupt the heap or stack of an unrelated process. This ensures that a failure in one process does not cause everything else to fail.
  • Scalability Across Distributed Systems: While threads are inherently limited to a single physical machine (as they rely on shared local memory), processes can easily be distributed across a cluster or a network of machines. This allows for scaling across different hardware.
  • Security and Privilege Separation: Multi-processing allows for the strict application of the Principle of Least Privilege. Different processes can be executed with distinct user permissions or security contexts.   • True Hardware Parallelism (CPU-Bound Tasks): In many interpreted languages (notably Python with its Global Interpreter Lock), threads cannot run in parallel on multiple cores (less true recently). This slide answers the question raised on the last slide: if threads share memory for free, how do separate processes talk to each other? Each process lives in its own isolated virtual address space. That isolation is good for security and stability, because one process cannot corrupt another. But sometimes you need to pass information between them, and there are two main ways to do it.

The first is shared memory. The operating system maps a single block of physical memory into the virtual address spaces of two or more distinct processes, so each one sees the same bytes at some address of its own. The second is message passing, such as signals and pipes. These are streams or interrupts that the operating system mediates.

The figure, from the KU Leuven course page at https://kuleuven-diepenbeek.github.io/osc-course/ch6-tasks/interprocess/, shows two memory layouts side by side. On the left, for message passing, process A and process B sit at the top of memory. Both have arrows going down into a message queue inside the kernel region, which holds messages m_0, m_1, up to m_n. Every message travels through the OS. On the right, for shared memory, a shared region sits between process A and process B, and both point directly into it. The kernel sits separately at the bottom and is not in the data path.

The tradeoff is this. Message passing is simpler and safer, but every transfer costs a system call and a copy. Shared memory is very fast, but you must coordinate access yourself, which is why semaphores appear later in this lecture.

// Producer (a process which puts data inside of the shared memory)

#include <stdio.h>

#include <stdlib.h>

#include <string.h>

#include <fcntl.h>

#include <unistd.h>

#include <sys/shm.h>

#include <sys/mman.h>

int main() {

const int SIZE = 4096; /* buffersize (bytes) */

const char *name = "OS"; /* shared memory object name */

const char *data_0 = "Hello";

const char *data_1 = "World!";

int shm_fd; /* shared memory file descriptor */

void *ptr;

/* create the shared memory file descriptor */

shm_fd = shm_open(name, O_CREAT | O_RDWR, 0666);

/* configure the size of the shared memory file */

ftruncate(shm_fd, SIZE);

/* memory map the shared memory file */

ptr = mmap(0, SIZE, PROT_WRITE, MAP_SHARED, shm_fd, 0);

/* write to the shared memory file */

sprintf(ptr,"%s",data_0);

ptr += strlen(data_0);

sprintf(ptr,"%s",data_1);

ptr += strlen(data_1);

return 0;

}

// CONSUMER (which uses the data it gets from the producer)

#include <stdio.h>

#include <stdlib.h>

#include <fcntl.h>

#include <unistd.h>

#include <sys/shm.h>

#include <sys/mman.h>

int main() {

const int SIZE = 4096; /* buffersize (bytes) */

const char *name = "OS"; /* shared memory object name */

int shm_fd; /* file descriptor */

void *ptr;

/* open the shared memory file */

shm_fd = shm_open(name, O_RDONLY, 0666);

/* memory map the shared memory file */

ptr = mmap(0, SIZE, PROT_READ, MAP_SHARED, shm_fd, 0);

/* read from the shared memory file */

printf("%s",(char *)ptr);

/* remove the shared memory file */

shm_unlink(name);

return 0;

}

Lecture notes

This slide puts the shared memory idea from the previous slide into real POSIX C code. It shows two programs side by side. On the left is the producer, a process that writes data into shared memory. On the right is the consumer, a process that reads that data. Both use the same two constants: SIZE = 4096 bytes and the shared memory object name "OS". That common name is how the two separate processes find the same block of memory.

The producer takes four steps. First, shm_open(name, O_CREAT | O_RDWR, 0666) creates the object for reading and writing, with read and write permission for everyone, and returns a file descriptor. Second, ftruncate(shm_fd, SIZE) sets the object's size to 4096 bytes. A newly created object has size zero, so you must set it before mapping. Third, mmap(0, SIZE, PROT_WRITE, MAP_SHARED, shm_fd, 0) maps the object into the producer's virtual address space and returns a pointer, ptr. MAP_SHARED is the important flag, because it makes your writes visible to other processes. Fourth, sprintf writes "Hello" at ptr, the code advances ptr by strlen("Hello"), and then it writes "World!". The memory now holds "HelloWorld!" with no space between the words.

The consumer opens the same name with O_RDONLY and maps it with PROT_READ. It then calls printf to print the string, and calls shm_unlink(name) to remove the object. Until something unlinks it, the object stays in /dev/shm even after the producer exits.

Notice that nothing here coordinates timing. You must run the consumer after the producer has finished writing. That gap is why later slides add semaphores. The next slide shows the robot's own processes sharing memory in this same way.

32. Threads & Processes – Race Conditions (1/2)

Race conditions, imagine you have the following code where I have multiple threads running at the same time?

int counter = 0;

void* doSomeThing(void *arg) {

int local_id; // new, per-thread variable

counter += 1;

local_id = counter; // make a local copy of counter for this thread

return NULL;

}

Lecture notes

This slide introduces race conditions with a short C example. The text asks you to imagine several threads running this code at the same time. The code declares a global variable, int counter = 0, outside any function. Below it is a thread function, void* doSomeThing(void *arg). Inside, it declares int local_id, commented as a new, per-thread variable. It then runs counter += 1, followed by local_id = counter, commented as making a local copy of counter for this thread, and finally returns NULL. The slide ends with a warning: you must think at a very low level, because the operating system can switch between threads at every assembly instruction of the compiled code, not just between lines of C.

The key distinction is where each variable lives. counter is global, so every thread shares the same memory location. local_id is declared inside the function, so it sits on each thread's own stack. The intent is that each thread gets a unique ID: the first thread sees 1, the second sees 2, and so on.

The catch is that the scheduler does not respect your C line boundaries. Between counter += 1 and local_id = counter, another thread can run and change counter. Before you look at the next slide, try to find an ordering of two threads that gives both of them local_id = 2.

This is the same concern behind the semaphores in the previous slide's shared-memory diagram. Whenever two processes or threads touch shared data, you have to ask what happens if they interleave. The next slide walks through exactly that failure.

33. Threads & Processes – Race Conditions (2/2)

The problem is the following:

// Code that both threads will execute:

counter += 1;

local_id = counter;

// -----------------------------------

// Thread 1

counter += 1; // after this, counter == 1

// Before Thread 1 can execute local_id = counter, it is paused by the CPU

// Thread 2

counter += 1; // after this, counter == 2

local_id = counter; // thus, in Thread 2, local_id is correctly 2

// Here, the CPU switches back to Thread 1

// Thread 1

local_id = counter; // now, local_id is still 2, instead of 1... mission failed

This is called a race condition!

This happens when you the ordering of instructions is not what you expect! There is some randomness in the instruction call ordering, so you might not always get this problem.

Can the Red Board also have this problem?

Lecture notes

This slide walks through, step by step, how the counter code from the previous slide goes wrong. At the top, in code font, is the snippet both threads execute: counter += 1, then local_id = counter. Below it is one possible interleaving, with the Thread 2 lines indented to show the CPU has switched away from Thread 1.

Thread 1 runs counter += 1, so counter is now 1. Before Thread 1 can copy counter into its local_id, the operating system pauses it. Thread 2 then runs both lines: counter becomes 2, and its local_id is correctly 2. The CPU switches back to Thread 1, which now executes local_id = counter and also gets 2 instead of 1. The slide's comment says "mission failed." Two threads were meant to get unique IDs 1 and 2, but both got 2.

This is a race condition: the result depends on the order in which instructions from different threads happen to run. The scheduler decides when to switch threads, and that timing varies from run to run. So the bug is intermittent. Your code can pass every test and still fail later, which makes these bugs hard to find.

The slide ends by asking whether the Red Board can have this problem. Think about it before the answer: the F28379D has no operating system threads, but it does have interrupts. A timer or SPI interrupt service routine can preempt your main loop, or a lower-priority interrupt, partway through updating a shared global variable. That is the same hazard, so the answer is yes.

Next, you see that even counter += 1 by itself is not a single, atomic operation.

34. Threads & Processes (21/22)

The problem is that what we just did was not an atomic operation . This means that internally, it is not implemented with a single CPU instruction but rather out of a series of different operations / instructions.

Even simple, unassuming code can cause a race condition. For example, the following causes a race condition,

int counter = 0;

void* doSomeThing(void *arg) {

counter += 1;

return NULL;

}

What is causing the race condition in this case?

The “+= 1”, is causing the race condition! Since that is not a single operation!

// In simple pseudocode, counter += 1 or counter++ looks like this:

int temp = counter + 1; // temp is for example the CPU register here, and "counter" is the value in memory

counter = temp; // the register value is written back out to the memory

Lecture notes

This slide names the root cause of the race condition from the last two slides: the operation was not atomic. An atomic operation is one the CPU carries out as a single, indivisible instruction, so no other thread can run in the middle of it. Most C statements are not atomic. The compiler turns them into a series of instructions, and the scheduler can switch threads between any two of them.

The slide shows an even smaller example. A global variable is declared as int counter = 0, and a thread function doSomeThing does nothing except counter += 1, then return NULL. The slide asks what causes the race condition here. The answer is the "+= 1" itself, because it is not a single operation.

The slide breaks it into pseudocode. First, int temp = counter + 1, where temp stands for a CPU register and counter is the value in memory. Second, counter = temp, which writes the register back out to memory. Together this is a read-modify-write sequence.

Here is how it goes wrong with two threads. Thread 1 reads counter, which is 0, into its register and adds 1. Before it writes back, the CPU switches to Thread 2. Thread 2 also reads 0, adds 1, and writes 1. Thread 1 then resumes and writes its own 1. Both threads incremented, yet counter ends at 1 instead of 2. This is called a lost update. Because it depends on timing, it may appear only occasionally, which makes it hard to debug.

This also answers the Red Board question from the previous slide. If an interrupt service routine and your main loop both modify the same global variable, the interrupt can land in the middle of a read-modify-write in the same way.

Next you see the fix: a mutex, which protects a short critical section using a lock that is itself implemented with an atomic instruction.

35. Threads & Processes – Mutex and Locking (1/2)

We need a way to secure the important sections in a thread such that you can lock and unlock access for pieces of code for the threads.

The simplest method is called the mutex (Mutual Exclusion).

The behavior can be seen as the lock on a restroom door. If you are using the restroom, you lock the door. Others that want to occupy the restroom must wait until you’re finished and you unlock the door (and get out, after washing your hands).

Hence, the mutex has only two states: one or zero, on or off, locked or unlocked.

Internally the mutex is implemented as a single, atomic CPU instruction!

The number of code / instructions between locking and unlocking a mutex should be kept to a minimum. If you put your whole thread inside the mutex then you are just making all your threads run in serial again! Losing all the parallelization benefits!

You can still have a Deadlock problem (where threads lock each other out causing infinite waiting)

Lecture notes

This slide is all text, with key words in bold. It introduces the mutex, short for MUTual EXclusion, as the simplest way to lock and unlock access to the important sections of code that threads share.

The slide's analogy is a restroom door. When you use the restroom, you lock the door. Anyone else who wants in must wait until you finish, unlock the door, and leave (after washing your hands). A mutex works the same way and has only two states: one or zero, on or off, locked or unlocked.

This is the fix for the race condition from the last two slides. The problem there was that counter += 1 is not atomic: it is a read into a register, an add, and a write back, and the CPU can switch threads in between. The mutex works because the lock itself is implemented as a single atomic CPU instruction, so two threads can never both see the door as unlocked and grab it at the same moment. The protected region between lock and unlock is called the critical section.

The slide gives two cautions.

First, keep the critical section as short as possible. If you wrap your whole thread in the mutex, the threads simply take turns and run serially, and you lose all the benefit of parallelism.

Second, a mutex does not prevent deadlock. In a deadlock, threads lock each other out and wait forever. A classic case is thread A holding lock 1 while waiting for lock 2, while thread B holds lock 2 and waits for lock 1.

Quick check: where would you place the lock and unlock around counter += 1 and local_id = counter? The next slide shows exactly that with pthread_mutex_lock and pthread_mutex_unlock.

36. Threads & Processes – Mutex and Locking (2/2)

int counter;

pthread_mutex_t counter_lock;

void* doSomeThing(void *arg) {

unsigned long i = 0;

int local_id;

pthread_mutex_lock(&counter_lock);

counter += 1;

local_id = counter;

pthread_mutex_unlock(&counter_lock);

printf(" Job %d started\n", local_id);

for(i=0; i<(0xFFFFFFFF);i++);

printf(" Job %d finished\n", local_id);

return NULL;

}

Lecture notes

This slide applies the mutex from the previous slide to the racy counter code. At the top are two globals: int counter, and a pthread_mutex_t named counter_lock. The thread function doSomeThing declares an unsigned long loop variable i set to 0 and an int local_id. It then calls pthread_mutex_lock(&counter_lock), executes counter += 1, copies the result with local_id = counter, and calls pthread_mutex_unlock(&counter_lock). After unlocking, it prints "Job %d started" with local_id, runs an empty for loop from 0 to 0xFFFFFFFF (about 4.3 billion iterations) to simulate work, prints "Job %d finished", and returns NULL.

The key idea is that only the critical section is locked. The read-modify-write of counter happens while the thread holds the lock, so no other thread can interleave between the read and the write-back that slide 34 showed. Each thread then gets a unique ID.

Notice why local_id exists. If the printf statements used counter directly, another thread could increment it before the print runs. The thread therefore takes a private copy while still holding the lock.

The long loop and the prints are deliberately outside the lock, so all threads can run their "work" in parallel. Moving the loop inside the lock would make the threads run one after another, with no benefit from threading.

A common mistake is forgetting to initialize the mutex before use, either with pthread_mutex_init or with PTHREAD_MUTEX_INITIALIZER. Another is returning early without unlocking, which leaves other threads waiting forever.

Quick check: what output order would you expect from several threads, and what would change if the unlock came after the for loop?

37. Threads & Processes – Semaphores (1/4)

While the mutex is nice and simple, we can improve the thread synchronization techniuques using Semaphores!

This technique is useful in producer-consumer problems.

The producer has 1 or more threads to prepare data and put it in a limited amount of shared memory (an array for example)

The consumer wants to be able to read that ready data.

Now we want to have multiple producers be able to write to that shared memory at a given time if there is an open spot. If not wait!

Similarly, the consumers can read data from the shared memory if there is something there. If not wait!

Lecture notes

This slide introduces semaphores, a step up from the mutex you just saw. It is all text on a plain white background. It says the mutex is nice and simple, but semaphores improve thread synchronization, and they are especially useful in what are called producer-consumer problems.

The slide then defines the two roles. The producer is one or more threads that prepare data and place it into a limited amount of shared memory, for example an array. The consumer is the thread, or threads, that want to read that ready data. Two rules follow. Producers may write to the shared memory if there is an open spot; if not, they wait. Consumers may read if there is something there; if not, they wait.

Here is why a mutex alone is not enough. A mutex has only two states, locked or unlocked, so it protects one critical section at a time. It cannot count how many slots in the buffer are full or empty. In a producer-consumer setup, that count is exactly what you need to track.

A robot example: one thread receives LiDAR scans and drops them into a fixed-size array, while another thread pulls scans out to run SLAM. If the array fills up, the receiving thread must pause. If it empties, the SLAM thread must pause.

Quick check: what should happen if a consumer reads from an empty buffer without waiting? It reads stale or garbage data.

Next, you see why simply checking repeatedly with a mutex wastes CPU time, and how a semaphore avoids that.

38. Threads & Processes – Semaphores (2/4)

We want threads that want to read/write an item from/to the array can only do so if it is possible.

If not, the thread should be paused until it’s sure that it can make progress, instead of constantly checking.

To do this, we need a new type of lock that keeps track of who’s waiting for what to happen, which is called the semaphore.

We could have a mutex and check if the specific element has been changed or not; however, having a mutex locking and unlocking almost immediately to check that element, is called busy waiting or polling and is bad for performance as you’re doing a lot of unnecessary work.

Lecture notes

This slide is text only, with four short paragraphs under the title "Threads & Processes – Semaphores." It states the goal for the producer-consumer setup from the last slide. A thread that wants to read an item from the shared array, or write one into it, should only do so when that is actually possible. If it is not possible, the thread should be paused, not constantly checking, until it is sure it can make progress. The tool for this is a new type of lock, the semaphore, which keeps track of who is waiting for what to happen. The bold terms are paused, semaphore, busy waiting and polling.

Why not just use the mutex you already know? You could. A consumer could lock the mutex, look to see whether an array element has changed, unlock, and repeat. Locking and unlocking almost immediately over and over like this is called busy waiting, or polling. It hurts performance. The thread burns CPU time doing useless checks, and it keeps grabbing the lock that a producer needs in order to write the data.

A semaphore fixes this. A waiting thread is put to sleep, and it is woken only when another thread signals that something has changed.

Think of it this way on your Raspberry Pi. Suppose one thread is waiting for the next LiDAR scan. You want it asleep until the scan arrives, not spinning in a loop that steals time from your control code.

Quick check: what is wasted when a consumer polls an empty array with a mutex? It wastes CPU cycles, and it also creates contention for the lock.

39. Threads & Processes – Semaphores (3/4)

Semaphores are simply a counter, but one that can automatically pause/resume threads that use it.

It only has 2 operations (below is pseudocode for the functions):

  • Wait: continues if counter > 0 and decrements it by 1. If not waits until counter > 0
  • Post: increments counter by 1. Causes 1 of the waiting threads to un pause.

Can be used to help wait for data to arrive.

wait(semaphore v){

while(1){

atomic {

if (v > 0){

v--;

return;

}

}

}

}

post(semaphore v){

atomic {

v++;

return;

}

}

Lecture notes

This slide defines a semaphore: simply a counter that can automatically pause and resume the threads that use it. It has only two operations. Wait continues if the counter is greater than 0 and decrements it by 1; otherwise the thread waits until the counter is greater than 0. Post increments the counter by 1 and causes one of the waiting threads to unpause. The slide notes that this can be used to wait for data to arrive.

Below the text are two pseudocode functions. On the left, wait(semaphore v) runs a while(1) loop. Inside it, an atomic block checks if v > 0; if so, it does v-- and returns. On the right, post(semaphore v) has an atomic block that does v++ and returns.

"Atomic" means the check and the change happen as one indivisible step, so no other thread can sneak in between them. That is exactly what was missing in the race conditions we saw earlier.

A common point of confusion: the while(1) loop here only shows the logic, which is "keep trying until v > 0." A real semaphore does not spin. The operating system puts the waiting thread to sleep and wakes it on a post, which avoids the busy waiting described on the previous slide.

Think of the counter as the number of items or free slots available. In a producer-consumer setup, the producer posts each time it adds data, and the consumer waits before reading.

Quick check: if the counter starts at 0 and one thread calls wait, what happens? It blocks until someone posts.

40. Threads & Processes – Semaphores (4/4)

#include <stdio.h>

#include <pthread.h>

#include <semaphore.h>

#include <unistd.h>

sem_t signal_sem;

void* worker_thread(void* arg) {

printf("Collected sensor data...\n");

sleep(2); // Simulate the time it takes to read hardware sensors

printf("Finished reading.\n");

sem_post(&signal_sem); // Increments S to 1. Unblocks the main thread.

return NULL;

}

int main() {

pthread_t thread;

// Initialize the semaphore to 0

sem_init(&signal_sem, 0, 0);

printf("Start reading.\n");

pthread_create(&thread, NULL, worker_thread, NULL);

printf("Waiting for sensor reading...\n");

// Attempt to decrement S. Since S is 0, the CPU strictly blocks here.

sem_wait(&signal_sem);

printf("Data collected, processing!\n");

// Clean up memory

pthread_join(thread, NULL);

sem_destroy(&signal_sem);

return 0;

}

Lecture notes

This slide puts the semaphore operations from the previous slide into a complete C program. The left column has the includes (stdio.h, pthread.h, semaphore.h, unistd.h), a global semaphore declared as sem_t signal_sem, and a function called worker_thread. The right column has main.

Walk through main first. sem_init(&signal_sem, 0, 0) takes three arguments: the semaphore's address, a "pshared" flag, and the starting count. The flag 0 means the semaphore is shared only among threads of this process. The count 0 means nothing is available yet.

Main prints "Start reading." and then pthread_create launches worker_thread. Main prints "Waiting for sensor reading..." and calls sem_wait. Because the count is 0, main blocks there.

Meanwhile the worker prints "Collected sensor data..." and sleeps 2 seconds to mimic a slow hardware read. It then prints "Finished reading." and calls sem_post, which raises the count to 1. That wakes main, whose sem_wait decrements the count back to 0 and returns, so main prints "Data collected, processing!". Finally pthread_join waits for the worker to exit, and sem_destroy releases the semaphore.

Notice the order of the first prints. "Waiting for sensor reading..." and "Collected sensor data..." can appear in either order, because the scheduler decides which thread runs first. "Finished reading." always comes before "Data collected, processing!".

Unlike the spin loop in the last slide's pseudocode, a real sem_wait puts the thread to sleep in the kernel. The waiting thread uses no CPU, so there is no busy waiting.

A common mistake is initializing the count to 1. Quick check: what happens then? Main would not block, and it would "process" before the data exists. Remember to compile with -pthread.
