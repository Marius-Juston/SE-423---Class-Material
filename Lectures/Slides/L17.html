Currently we have the LiDAR working and returning points; however, what kind of data are missing from just the LiDAR?

Color, complex shapes, human vision like data

Vision processing allows a robot to extract rich, high-density data from its environment.

Instead of an array of 228 distances (like our LiDAR), a camera gives us millions of data points per frame (RGB per pixel).

What is the primary drawback of having millions of data points per frame in a real-time mechatronic system?

Lecture notes

This slide is text only, laid out as two questions, each followed by its answer. It moves us from the LiDAR, which you already have working, to cameras.

The first question asks what data is missing if the robot has only the LiDAR. The answer on the slide is color, complex shapes, and human-vision-like data. The LiDAR tells you how far away something is in each direction. It cannot tell you that the object is an orange ball or a blue box, and it sees only a thin slice of the world.

The slide then states that vision processing lets a robot extract rich, high-density data from its environment. Our LiDAR returns an array of 228 distances. A camera returns millions of data points per frame, because every pixel carries red, green and blue values. For scale, even a modest 640 by 480 image has 307,200 pixels. At three color values per pixel, that is about 921,600 numbers in a single frame, roughly 4,000 times the LiDAR scan.

The second question asks what the primary drawback of that much data is in a real-time mechatronic system. The answer is computational latency. Processing takes time, and you need more memory and bandwidth just to move and store each frame. In a feedback loop, latency acts like a time delay, and delay erodes stability margin. A perfect measurement that arrives late can still make your controller oscillate.

Keep that tradeoff in mind. Next, we ask whether a camera is an active or a passive sensor, and why that makes vision fragile.

Lecture notes

This slide continues the question-and-answer format from the previous one. It asks: is a standard camera an active or a passive sensor? The answer, centered on the slide, is passive. A camera does not emit energy; it only captures ambient light bouncing off objects. Because it is passive, it is highly vulnerable to environmental changes. The slide then asks what happens if the sun goes behind a cloud. The answer is that pixel colors change, shadows appear, and so on. It ends with an open question: how do we build robust code around this?

An active sensor sends out its own energy and measures what comes back. The LiDAR you already have working is active: it emits laser light and times the return, so it works the same in a bright room or a dark one. A camera has no light source of its own. The value of each pixel depends on the object's surface and also on the lighting in the room. The same orange ball can produce very different RGB numbers near a window than under a ceiling light.

So what does robust code look like? Avoid hard-coding raw RGB values. A common fix, which you will see in the pipeline on the next slide, is converting RGB to HSV. Hue (the color itself) stays fairly stable when brightness changes. Other useful steps are filtering out small noisy blobs by area and recalibrating your thresholds in the room where you actually run the robot.

9. Camera Vision (3/33)

The main pipeline that we will follow in this class is the following:

Step 1: The CMOS sensor captures photons and converts them to digital arrays.

Step 2: The processor filters the image (e.g., finding specific colors).

Step 3: The algorithm calculates the coordinates of the target (Centroid).

Step 4: The Cascade Control loop turns the coordinates into wheel velocities.

Lecture notes

This slide gives the roadmap for the rest of the lecture: the four-stage camera pipeline you use in this class. A flowchart runs left to right in four dashed boxes, with the four steps written below it.

Stage 1, Raw Sensor Data: a CMOS array converts photons to voltage. Over it sits a Bayer color filter array, a mosaic of 1 red to 2 green to 1 blue, so each pixel measures only one color.

Stage 2, Pre-Processing: demosaicing by bilinear interpolation fills in the two missing colors at every pixel. The image is then converted from RGB to HSV to isolate chrominance, the color itself, from brightness. A binary threshold keeps only pixels whose hue satisfies H_min <= H <= H_max. This answers the question from the last slide: separating hue from brightness makes color detection more robust when lighting changes.

Stage 3, Feature Extraction: blob detection with connected components groups neighboring "on" pixels. Area filtering discards blobs whose pixel count is too small to be more than noise. Image moments then give the centroid: x_bar = M_10/M_00 and y_bar = M_01/M_00. Here M_00 is the blob area, and M_10 and M_01 are the sums of the pixel x and y coordinates.

Stage 4, Control Logic: the error is e(t) = x_bar - X_center, the target's horizontal offset from the image center. A PI controller computes u(t) = K_p*e + K_i times the integral of e dt. This sets the wheel velocities v_left and v_right, which become PWM motor commands in a cascade loop.

12. Camera Vision (5/33)

Most modern robotics vision relies on CMOS (Complementary Metal-Oxide-Semiconductor) sensors.

A CMOS sensor contains a massive 2D grid of microscopic photodiodes.

When photons strike a photodiode, they excite electrons via the photoelectric effect, creating a measurable voltage.

This continuous voltage is sampled and converted into a discrete digital value (usually 0-255 for an 8-bit ADC).

Lecture notes

This slide has no figures, just four statements about how a camera turns light into numbers. It is the first stage of the pipeline from the previous slide's flowchart: the CMOS array converting photons to voltage.

First, most modern robotics vision uses CMOS sensors. CMOS stands for Complementary Metal-Oxide-Semiconductor, the same chip process used for microcontrollers like the F28379D. That is why the sensor, amplifiers and converters can all sit on one inexpensive chip.

Second, a CMOS sensor is a huge 2D grid of microscopic photodiodes. Each photodiode corresponds to one pixel, so a 640 by 480 camera has about 307,000 of them.

Third, when photons strike a photodiode, they excite electrons through the photoelectric effect. The more light that arrives during the exposure, the more charge collects. That charge is converted to a measurable voltage inside the pixel.

Fourth, that continuous voltage is sampled and converted to a discrete digital value, usually 0 to 255 with an 8-bit ADC. An n-bit converter gives 2^n levels, and 2^8 = 256. This is the same idea as the ADC you use on the Red Board, whose 12-bit converter gives 2^12 = 4096 levels. A camera simply does this for hundreds of thousands of channels every frame.

A common misconception is that a photodiode sees color. It does not: it only measures how much light hit it. Color comes from filters placed over the pixels, which you will see shortly.

Quick check: how many intensity levels does a 10-bit camera produce? The answer is 1024.

14. Camera Vision (7/33)

  • Readout performed by transferring one row at a time to the column storage capacitors, then reading out the row, one (or more) pixel at a time, using the column decoder and multiplexer
  • In many CMOS image sensor architectures, row integration times are staggerred by the row / column readout time (scrolling shutter)

https://isl.stanford.edu/~abbas/ee392b/lect04.pdf

Lecture notes

This slide zooms in on how a CMOS sensor actually reads out its pixels, building on the chip layout and block diagram from the previous slide. The figure, from Stanford's EE392b lecture notes, shows the pixel array as a grid. A row decoder on the left drives horizontal lines called word lines, and each pixel, a photodetector plus a few readout transistors, connects to one word line and one vertical bit line. Two rows at the top are outlined in red to show that a whole row is handled together. The bit lines run down into a strip of column amplifiers and capacitors, then into a column multiplexer, which feeds a single output amplifier.

The readout works in two steps. First, the row decoder selects one row, and every pixel in that row dumps its voltage down its bit line onto that column's storage capacitor, all at once. Second, the column multiplexer steps across those capacitors, sending one pixel (or a few) at a time to the output and on to the ADC. Then the next row is selected and the process repeats.

Because rows are read one after another, many sensors also start and stop each row's exposure (its integration time) staggered by that row readout time. This is called a rolling or scrolling shutter. The top of the image is captured slightly earlier than the bottom. If your robot turns quickly or an object moves fast, vertical edges appear slanted or wobbly. Global-shutter sensors expose every pixel simultaneously but cost more. Most low-cost camera modules, like those commonly paired with a Raspberry Pi, use a rolling shutter.

It assigns each pixel to capture only Red, only Green, or only Blue light.

https://en.wikipedia.org/wiki/Bayer_filter

Lecture notes

This slide answers the question from the last slide: how does a colorblind sensor array see red, green and blue at the same time? The answer is to place a microscopic color filter over each individual photodiode. This layer of filters is called a Color Filter Array, or CFA, and the most common one is the Bayer filter. It assigns each pixel to capture only red, only green, or only blue light.

On the left is an isometric drawing of a Bayer filter. A checkerboard of red, green and blue squares, one per pixel, sits on top of the gray sensor grid. Part of the filter layer is cut away to show the bare photosites beneath.

On the right are three photosites side by side. Red, green and blue light arrows arrive at each one from above. The first has a red filter, and only the red arrow continues down into the gray photodiode. The second passes only green, and the third passes only blue.

Under each photosite is a small 6 by 6 grid showing where that color's pixels sit in the mosaic:

1. Red pixels fill every other position on every other row.

2. Green pixels form a full checkerboard.

3. Blue pixels fill the leftover alternate positions.

The key idea is that each photodiode still measures only intensity. The filter simply decides which wavelengths reach it. So every pixel records one color's brightness, never all three.

The simplest implementation of the algorithm for the Connected Components work is as following:

  1. The algorithm scans the image pixel by pixel (raster scan).
  2. When it finds a '1', it checks the neighboring pixels (usually 4-connectivity or 8-connectivity).
  3. If a neighbor is also a '1', it assigns them the same "Label" (e.g., Object A).
  4. It uses a "Union-Find" data structure to merge labels if two separate groups eventually connect.

This slide answers the question from the last slide: which simple graph algorithm helps find blobs? It is text only, listing four steps for the simplest Connected Component Labeling algorithm, plus a note that you can think of it as Breadth-First Search.

The slide carries on from the image moments. Now that you have the centroid (x-bar, y-bar), you can turn it into a steering command.
