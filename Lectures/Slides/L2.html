7. Registers

Lecture notes

This section title slide reads "Registers" in large dark blue text on an orange background, with faint hand-drawn equations and sketches behind it and the Illinois logo in the corner.

With the course logistics and the semester project covered, you now move into the technical core of Lecture 2: how the TMS320F28379D's CPU controls its peripherals. The next slide explains why that works: on this chip, peripherals live at memory addresses, just like RAM and flash.

8. Memory-Mapped I/O

The CPU only knows one thing: memory addresses

On the TMS320F2837xD:

  • RAM has addresses
  • Flash has addresses
  • Peripherals also have addresses

This is called Memory-Mapped I/O (MMIO)

A peripheral is a hardware module whose control and status registers are mapped to fixed memory addresses, allowing the CPU to configure and control hardware by reading from and writing to memory.

Lecture notes

This slide is titled Memory-Mapped I/O. It is text only, with no figures. The opening line, in bold, says the CPU only knows one thing: memory addresses. A short list then notes that on the TMS320F2837xD, RAM has addresses, Flash has addresses, and peripherals also have addresses. This arrangement is called Memory-Mapped I/O, abbreviated MMIO. The slide ends with a definition: a peripheral is a hardware module whose control and status registers are mapped to fixed memory addresses, so the CPU configures and controls hardware simply by reading from and writing to memory.

We just introduced registers, and this slide explains how the CPU reaches them. The processor has no special "talk to the PWM" instruction. Every load and store goes to an address. Some addresses land in RAM, where your variables live. Some land in Flash, where your program is stored. Others are wired to the control and status registers of the GPIO, timers, ePWM, ADC, and so on. Writing a number to one of those addresses can turn on a pin or start a timer. Reading from one tells you whether a conversion is finished.

One common surprise is that a peripheral register does not behave like ordinary memory. Its value can change on its own, for example when a status flag is set by hardware. A write can also trigger an action. This is why TI's header files declare these registers volatile, so the compiler never skips or reorders those reads and writes.

Next, we look at how these registers are organized into system and peripheral registers, each found at a base address plus an offset.

9. System and Peripheral Registers

Peripheral:

A Peripheral is a hardware device with a specific address in memory that it writes data to and/or reads data from.

All peripherals can be described by an offset from the Peripheral Base Address.

On the TMS320F2837xD, registers are typically 32-bits or 16-bit wide

Each bit usually represents to:

  • A hardware switch (ON / OFF)
  • A configuration option
  • A hardware status flag ( Error code, OK )
Lecture notes

This slide, titled "System and Peripheral Registers," is text only. It defines a peripheral as a hardware device with a specific address in memory that data is written to and read from. It states that every peripheral can be described by an offset from the Peripheral Base Address, that registers on the TMS320F2837xD are typically 32 or 16 bits wide, and that each bit usually represents one of three things: a hardware switch (on or off), a configuration option, or a hardware status flag such as an error code or an OK indication.

This builds directly on the memory-mapped I/O idea from the previous slide. Because the CPU only understands addresses, a peripheral such as a timer, the ADC, or a GPIO port is controlled entirely through registers that sit at fixed locations. Writing to one of those locations configures or commands the hardware. Reading from one tells you what the hardware is doing.

Inside a register, think of each bit, or small group of bits, as a labeled field. A switch bit might enable a peripheral's clock. A configuration field might select a clock divider or set a pin as input or output. A status flag is set by the hardware itself, for example to say a conversion finished or an error occurred, and your code reads it.

A common mistake is to treat a register as a single number. Writing a whole new value to it can unintentionally change neighboring bits you meant to leave alone. That is why later in this lecture we cover bits, masks, and bitwise operations.

Next, we look at how the Peripheral Base Address and the register offset combine to locate each register.

10. Peripheral Base Address

TI groups peripherals into address regions.

For example:

  • GPIO register live in one address range
  • Timers in another
  • ePWM in another
  • ADC (Analog to Digital Converters ) in another
  • Etc…

Each register is located at:

Peripheral Base Address + Register Offset

You do not need to calculate these addresses manually; TI provides C structures and header files that do this manually.

EPwm1Regs.TBCTL.bit.CLKDIV = 1;

Lecture notes

This slide answers a practical question from the last one: if every peripheral lives at memory addresses, how is that memory organized? The slide says TI groups peripherals into address regions. The GPIO registers live in one address range, the timers in another, ePWM (enhanced pulse width modulation) in another, the ADCs (analog to digital converters) in another, and so on.

The key rule, shown in bold and centered, is that each register is located at Peripheral Base Address + Register Offset. The base address is where a peripheral's block of registers starts. The offset is how far a particular register sits from that start. For example, ePWM1 and ePWM2 have identical register layouts at different base addresses, so the same offset selects the same register in either module.

The slide then says you do not need to calculate these addresses by hand. The words "addresses manually" are a hyperlink to further reading. TI provides C structures and header files that do the calculation for you. At the bottom is one line of code: EPwm1Regs.TBCTL.bit.CLKDIV = 1;

Read it left to right. EPwm1Regs is a structure placed at ePWM1's base address. TBCTL is the Time-Base Control register at its offset. ".bit" gives access to named bit fields. CLKDIV is the clock-divide field inside TBCTL. The compiler turns all of this into "write these bits at base plus offset," so you never type a raw address.

A common mistake is assuming every register can be written this way at any time. The next slides cover system registers that are protected and need EALLOW before you can write to them.

11. System Peripheral

System registers control the behavior of the CPU itself

These registers affect the entire chip. These system registers are protected.

These can modify:

  • Clock configuration
  • Resets
  • Peripheral interrupts
  • Memory configuration
  • Timer

Full list is available in Table 3-17 - System Control Base Address Table

Lecture notes

This slide, titled "System Peripheral," introduces the second kind of register from slide 9. The text says system registers control the behavior of the CPU itself, that they affect the entire chip, and that they are protected. They can modify five things: clock configuration, resets, peripheral interrupts, memory configuration, and the timer. The last line links to Table 3-17, the System Control Base Address Table, which has the full list.

The key idea is scope. A peripheral register, like the ePWM register on slide 10, changes one module. A system register changes how the whole microcontroller runs. Clock configuration sets the system clock and which peripherals receive a clock at all. If a module's clock is off, writes to its registers do nothing. Resets include the watchdog, which restarts the chip if your code stops servicing it. Peripheral interrupts are routed through the PIE, the Peripheral Interrupt Expansion block. Its vector table tells the CPU which function to run for each interrupt. Memory configuration decides how RAM blocks are assigned. On this dual-core F28379D, that includes which RAM belongs to CPU1 and which to CPU2.

A wrong write to these registers can stall the clock or send an interrupt to a garbage address. That is why they are protected, and the next slide shows how: the EALLOW and EDIS instructions.

A common mistake is writing to a protected register without EALLOW. The write is silently ignored, so nothing errors and nothing changes.

Use the Table 3-17 link when you need to find which system register controls a feature.

12. EALLOW / EDIS

Some registers are protected to prevent accidental damage ( most / all system peripherals ).

Thus, an additional layer of protection is allowed for accidental writes ( memory leaked code or otherwise ).

  • EALLOW: unlocks protected registers
  • EDIS: locks them again

EALLOW; // This is needed to write to EALLOW protected registers

PieVectTable.TIMER0_INT = &cpu_timer0_isr;

PieVectTable.TIMER1_INT = &cpu_timer1_isr;

PieVectTable.TIMER2_INT = &cpu_timer2_isr;

PieVectTable.EMIF_ERROR_INT = &SWI_isr;

EDIS; // This is needed to disable write to EALLOW protected registers

Lecture notes

This slide explains how the protected system registers from the previous slide are actually written. The text says some registers, including most or all system peripherals, are protected to prevent accidental damage. This extra layer guards against accidental writes, for example from code that leaks memory or writes through a bad pointer. Two keywords control the protection. EALLOW unlocks protected registers, and EDIS locks them again.

Below that is a code block. It starts with the line EALLOW; with the comment "This is needed to write to EALLOW protected registers." Four assignments follow. PieVectTable.TIMER0_INT = &cpu_timer0_isr, and the same pattern for TIMER1_INT and TIMER2_INT with cpu_timer1_isr and cpu_timer2_isr. The last assignment is PieVectTable.EMIF_ERROR_INT = &SWI_isr. The block ends with EDIS; and the comment "This is needed to disable write to EALLOW protected registers."

The PIE vector table tells the CPU which function to run when each interrupt fires. Each line stores the address of an interrupt service routine (ISR), which is why the ampersand appears. Here, the otherwise unused EMIF error slot is borrowed to hold a software interrupt routine, SWI_isr. Changing this table could crash the whole chip, so it is protected.

EALLOW and EDIS are single CPU instructions. They set and clear a protection bit in a CPU status register.

A common mistake is forgetting EALLOW. Writes to protected registers are then silently ignored, and no error tells you why your setting never took effect. The opposite habit to build is calling EDIS right away, so the window where the registers are unlocked stays as small as possible.

Next, you'll see that ordinary peripheral registers like GPIO usually need no such unlocking.

13. Peripheral Registers

Peripheral registers control individual hardware modules. Usually do not have any write protection

Examples:

  • GPIO (General Purpose Input-Output)
  • Timers
  • ADC (Analog-to-Digital Converter)
  • PWM (Pulse Width Modulation)
  • SPI (Serial Peripheral Interface)

Each peripheral has a Read (DAT), Write (SET), Clear (CLEAR) and Toggle (TOGGLE) register.

GpioDataRegs.GPBDAT.bit.GPIO37; // Do not use to set

GpioDataRegs.GPBSET.bit.GPIO37 = 1; // Sets GPIO37 to 1

GpioDataRegs.GPBCLEAR.bit.GPIO37 = 1; // Sets GPIO37 to 0

GpioDataRegs.GPBTOGGLE.bit.GPIO37 = 1; // Sets GPIO37 to 0->1

Lecture notes

This slide contrasts peripheral registers with the protected system registers from the last two slides. The text says peripheral registers control individual hardware modules and usually have no write protection, so you do not need EALLOW and EDIS to use them. The examples listed are GPIO (General Purpose Input-Output), Timers, ADC (Analog-to-Digital Converter), PWM (Pulse Width Modulation), and SPI (Serial Peripheral Interface).

The slide then states that each peripheral has a Read register (DAT), a Write register (SET), a Clear register (CLEAR), and a Toggle register (TOGGLE). Four lines of C code show this for GPIO pin 37:

GpioDataRegs.GPBDAT.bit.GPIO37, commented "Do not use to set."

GpioDataRegs.GPBSET.bit.GPIO37 = 1, which sets GPIO37 to 1.

GpioDataRegs.GPBCLEAR.bit.GPIO37 = 1, which sets GPIO37 to 0.

GpioDataRegs.GPBTOGGLE.bit.GPIO37 = 1, which flips GPIO37, for example from 0 to 1.

GPIO37 uses the "GPB" registers because pins are grouped into ports of 32. Port A covers GPIO0 to 31, and port B covers GPIO32 to 63.

Notice that the CLEAR line writes a 1 to drive the pin to 0. In SET, CLEAR, and TOGGLE, writing 1 means "perform this action on this bit." Writing 0 does nothing, so the other pins are unaffected. Use DAT to read a pin's current state.

Quick check: if GPIO37 is currently high and you write 1 to GPBTOGGLE.bit.GPIO37, what is the pin afterward? It goes low.

Why not just write to DAT to set a pin? That is the topic of the next slide: writing DAT is a read-modify-write sequence that an interrupt can corrupt.

14. Using DAT

There are problems that arise from writing directly to DAT

Writing to DAT requires,

  1. Read
  2. Modify
  3. Write

An interrupt ( code that runs on certain events ) can run between these steps and corrupt data

SET / CLEAR registers avoid this by being atomic hardware operations.

Atomic operations guarantee that a variable will be locked during the operations and cannot be modified by anyone else during that time.

Lecture notes

This slide is text only, titled "Using DAT." It states that writing directly to a DAT register causes problems, because a write to DAT takes three steps: 1, read; 2, modify; 3, write. An interrupt, meaning code that runs automatically when certain events happen, can run between these steps and corrupt data. SET and CLEAR registers avoid this because they are atomic hardware operations. The word "atomic" is in bold. The last line defines atomic operations: they guarantee that a variable is locked during the operation and cannot be modified by anyone else during that time.

This explains the warning on the previous slide, where GPBDAT carried the comment "Do not use to set." Suppose you write GpioDataRegs.GPBDAT.bit.GPIO37 = 1. You only change one bit in the C code, but the CPU cannot change a single bit in memory. It reads the entire 32-bit GPBDAT register, ORs in bit 5 (GPIO37 is bit 5 of port B, since port B starts at GPIO32), and writes all 32 bits back. Now suppose a timer interrupt fires right after the read and sets GPIO40 to light an LED. When your main code resumes, it writes back its stale copy, which still has GPIO40 at 0. The LED change silently disappears. Bugs like this are intermittent and very hard to find.

SET and CLEAR work differently. Writing a 1 to a bit changes only that pin, and writing a 0 does nothing, so the hardware never has to read the register first. The change happens in a single write that nothing can interrupt.

Quick check: why is GPBTOGGLE also safe to use from both main code and an interrupt?

15. Digital I/O (GPIO)

Each physical pin can serve multiple functions

  • GPIO
  • PWM
  • SPI
  • SCI
  • CAN

You must first select the function

GPIO_SetupPinMux(31, GPIO_MUX_CPU1, 0);

GPIO_SetupPinOptions(31, GPIO_OUTPUT, GPIO_PUSHPULL);

Lecture notes

This slide covers the step that comes before you can toggle a pin: telling the chip what that pin is for. The title is "Digital I/O (GPIO)." The text says each physical pin can serve multiple functions; "multiple functions" is a clickable link to the pin multiplexing reference. Five functions are listed: GPIO, PWM, SPI, SCI and CAN. The slide then says "You must first select the function" and shows two lines of C code: GPIO_SetupPinMux(31, GPIO_MUX_CPU1, 0); and GPIO_SetupPinOptions(31, GPIO_OUTPUT, GPIO_PUSHPULL);

The chip has far more internal peripherals than physical pins, so each pin connects to a multiplexer, or mux, a hardware switch that routes one of several signals to the pin. In the first call, 31 is the pin number, GPIO_MUX_CPU1 means CPU1 owns the pin, and the last argument, 0, is the mux index. Index 0 selects plain GPIO. Other index values route the pin to peripherals such as an ePWM output or an SPI line, and the pin mux table behind the link tells you which index gives which function.

The second call configures the pin as an output and selects push-pull drive. Push-pull means the pin actively drives both high and low, as opposed to open-drain, which only pulls low.

A common mistake is writing to GpioDataRegs.GPxSET for a pin you never configured. The pins start up as inputs, so nothing happens. Configure the pin first, then use the SET, CLEAR and TOGGLE registers from the last two slides.

Lecture notes

This is a section divider slide titled "Bits," shown in dark blue on the orange Illinois background with faint hand-drawn engineering sketches. The sketches are decorative only.

17. Binary

The CPU only reads binary, 1s or 0s; however, for humans it is difficult to understand long string of numbers.

A 32-bit register could be represented as such with 32 bits (unsigned 3,357,083,684):

int32_t x = 0b110010000001100100000100000100100;

What is a potential problem?

Prone to make mistakes if you need to manually type this out! For example, there are 33-bits above, not 32!

Why not use Decimal system? Not as simple to convert from decimal to binary!

Lecture notes

This slide gives the motivation for hexadecimal, which comes next. It makes three points. The CPU only works with binary, ones and zeros, but long strings of binary digits are hard for people to read. A 32-bit register can be written out as 32 bits; the slide's example is the unsigned value 3,357,083,684, written in C as int32_t x = 0b110010000001100100000100000100100, where the 0b prefix marks a binary literal. Then the slide asks: what is a potential problem?

Pause and try counting the digits before the answer appears. The answer is that typing binary by hand is very error prone. The literal on the slide actually has 33 bits, not 32. An extra zero slipped into the lower bits, so the value the compiler sees is not the intended 3,357,083,684. Errors like this are easy to make when you write register values to configure GPIO pins or peripherals, and they are hard to spot.

The slide then asks: why not just use decimal? Converting between decimal and binary takes real arithmetic, because powers of ten do not line up with bit boundaries. Looking at 3,357,083,684, you cannot tell which bits are set.

A small detail: a value above about 2.1 billion does not fit in a signed int32_t. For an unsigned register value like this, uint32_t is the matching type.

Next, hexadecimal fixes both problems, because each hex digit maps to exactly four bits.

18. Hexadecimal

Instead of base 10, let’s explore base 16, i.e., hexadecimal base system

Very easy to convert binary to hex (0-9 then A-F):

BinaryHexidecimalDecimal
000000
000111
1010A10
1111F15

Every 4-bits = 1 hex value, makes things much easier to compress, much easier to look at!

int32_t x = 0xC8190824;

int16_t x = 0x0824;

Windows Calculator set to programming mode can easily do the conversion!

Lecture notes

This slide introduces hexadecimal, or base 16, as the fix for the problem on the previous slide: long binary strings are hard to read and easy to mistype.

The slide shows a three-column table with the headers Binary, Hexadecimal and Decimal. Its rows are: 0000 is hex 0, decimal 0. 0001 is hex 1, decimal 1. 1010 is hex A, decimal 10. 1111 is hex F, decimal 15. Hex digits run 0 through 9 and then A through F for the values 10 through 15. That gives exactly 16 symbols, which is every pattern four bits can make.

The key idea is that every 4 bits map to exactly one hex digit. To convert, group the binary into nibbles (a nibble is 4 bits) starting from the right, then replace each nibble with its digit. Take the 32-bit value from the last slide: 1100 1000 0001 1001 0000 1000 0010 0100 becomes C 8 1 9 0 8 2 4, which is 0xC8190824, or 3,357,083,684 in decimal. The 0x prefix tells C the number is hex. A 32-bit register is always eight hex digits, so a missing or extra digit is easy to spot. That is how hex avoids the 33-bit typo from the previous slide.

The second example, int16_t x = 0x0824, is the lower 16 bits of that same value: four hex digits, decimal 2084.

A common mistake: 0xC8190824 is larger than the maximum int32_t, which is 2,147,483,647. When you store register values, you usually want an unsigned type such as uint32_t.

To check your work, set the Windows Calculator to Programmer mode, which converts between binary, hex and decimal. Next, you use hex to build bit masks.

19. Bits, Bit Positions and Masks

Bit number starts at 0

Bit 0 → 20

Bit 1 → 21

Bit 5 → 25 = 32 = 0x20

Creating a bit shifting:

  • Left shifting: x << n, shifts bits in x to the left by n. 0b01 << 1 = 0b10
  • Right shifting: x >> n, shifts bits in x to the right by n. 0b10 >> 1 = 0b01

Commonly used to create bit “masks”:

int32_t bit5Mask = 1 << 5; // 0x20, sets only bit 5 to 1!

What are masks? What are they used for?

Lecture notes

Now that you can read binary and hexadecimal, this slide shows how to point at one specific bit in a register and build a value that targets only that bit.

The slide first states that bit numbering starts at 0, with the rightmost, least significant bit as bit 0. Each bit position n carries a weight of 2 to the power n. Bit 0 is 2^0, which equals 1. Bit 1 is 2^1, which equals 2. Bit 5 is 2^5, which equals 32, or 0x20 in hex. A common mistake is counting bits from 1, which puts you one position off and has you writing the wrong field in a register.

Next come the shift operators. Left shift, written x << n, moves every bit in x left by n places and fills in zeros, so 0b01 << 1 = 0b10. Right shift, written x >> n, moves bits right by n, so 0b10 >> 1 = 0b01. Shifting left by n multiplies by 2^n, and shifting right by n divides by 2^n.

The code line on the slide reads: int32_t bit5Mask = 1 << 5; with the comment "0x20, sets only bit 5 to 1." This is a mask, a value with ones only in the bit positions you care about. The slide closes with the questions "What are masks? What are they used for?" The answer is that masks let you test, set, clear or toggle selected bits in a register without disturbing the others. This slide answers the question from the last slide, "what are masks used for?" It shows four C bitwise operations, each applied to bit 3 of a variable called reg using the mask 1 << 3, which is 0b1000 or 0x08.

On the left, AND (&) is used for masking, or testing a bit: if (reg & (1 << 3)) { // Bit 3 is set }. The result is nonzero only if bit 3 of reg is 1. Below that, OR (|) sets a bit: reg |= (1 << 3) forces bit 3 to 1 and leaves the others alone. On the right, NOT (~) combined with AND clears a bit: reg &= ~(1 << 3). The NOT flips the mask to all ones except bit 3, so the AND forces bit 3 to 0 and keeps every other bit. Finally, XOR (^) toggles a bit: reg ^= (1 << 3) flips bit 3.

A truth table at the bottom left lists columns REG, MASK, AND, OR and XOR. For REG 0 and MASK 0, all results are 0. For 0 and 1: AND 0, OR 1, XOR 1. For 1 and 0: AND 0, OR 1, XOR 1. For 1 and 1: AND 1, OR 1, XOR 0. A smaller table on the right shows NOT: MASK 0 gives 1, and MASK 1 gives 0.

The key pattern is that a mask selects the bits you touch. Where the mask is 0, OR and XOR leave reg unchanged. Where the mask is 1, AND leaves reg unchanged.

Watch two common mistakes. First, & and | are not the logical operators && and ||. Second, ~ is not !, because !(1 << 3) is just 0.

Lecture notes

This slide answers the question in its title with text only, no figures. It opens by comparing a timer to an ordinary clock and stresses that in hardware timers are extremely important. It then defines a timer as a hardware counter that does two things: it counts clock cycles, and it triggers an interrupt when it reaches a specified condition.

The TMS320F2837xD on your Red Board has three 32-bit CPU timers. CPU-Timer0 and CPU-Timer1 are free for your applications. CPU-Timer2 is normally reserved for a real-time operating system, but if no operating system is using it, your application can use it too. Why do timers matter so much? Feedback control needs to sample sensors and update outputs at a fixed, predictable rate, and a timer interrupt gives you that rate without the CPU waiting in a loop. The numbers make this concrete. At 200 MHz, one clock cycle is 1/200,000,000 seconds, or 5 nanoseconds. A 1 millisecond interrupt therefore corresponds to about 200,000 counts. A full 32-bit count of 2^32 cycles lasts roughly 21.5 seconds, so a single timer covers a very wide range of periods.

Quick check: how many SYSCLK cycles occur in 4 ms? (Answer: 800,000.)

This slide shows Figure 3-10, "CPU-Timers," the block diagram of one CPU timer from the TI TMS320F2837xD reference manual. Red arrows label three logic gates: two OR gates at the top and an AND gate on the left whose lower input has a small circle, labelled NOT, meaning that input is inverted.

Follow the clock from left to right. SYSCLKOUT, the 200 MHz system clock, enters the AND gate with TCR.4, the Timer Stop Status bit in the Timer Control Register. Because TCR.4 is inverted, clock pulses pass only while TCR.4 = 0. Writing 1 stops the timer, and writing 0 starts it. A timer does nothing until your software explicitly starts it.

The gated clock drives the 16-bit prescale counter, PSCH:PSC. It counts down, and when it underflows it produces a "borrow." That borrow does two things. It reloads the prescaler from the 16-bit divide-down register, TDDRH:TDDR, and it decrements the main 32-bit counter, TIMH:TIM, by one. The prescaler therefore slows time down so the main counter ticks at a manageable rate, once every TDDR + 1 clock cycles.

The 32-bit counter decrements on each prescaled tick. When it underflows, its borrow asserts TINT, the timer interrupt; the bar over the name means it is active low. The same borrow reloads the counter from the 32-bit period register, PRDH:PRD, so the timer repeats forever. The OR gates also force both reloads whenever Reset or Timer reload is asserted.

Quick check: if TCR.4 = 1, does TIM ever change? No. This is a common reason a lab interrupt never fires.

The 16-bit divide-down register (TDDRH:TDDR) divides the incoming clock frequency so the timer runs at a manageable speed. The 16-bit prescale counter (PSCH:PSC) counts down. When it underflows, it produces a borrow and reloads from TDDR. That borrow advances the main 32-bit timer, so the prescaler slows time down before it reaches the main counter.

The 32-bit period register (PRDH:PRD) holds the value the timer reloads from. The 32-bit counter (TIMH:TIM) is the actual counter, and it decrements every prescaled tick. When it reaches zero, a borrow occurs, an interrupt (TINT) is generated, and the counter reloads from PRD.

25. What is a timer? (4/6)

Why are there 2-counter blocks?

System clock: SYSCLKOUT = 200 MHz → Tclk = 2 ns

Problem is that the clock is too fast for software:

At 200 MHz:

  • 1 ms requires: 200,000 clock ticks
  • 10 ms requires: 2,000,000 clock ticks

Split the job into 2 counters:

  • Prescaler Counter (PSC, TDDR) – Controls speed, defines a unit of time
  • Main Timer Counter (TIM, PRD) – Controls duration, how much time should pass

One counter decides how fast time flows and the other decides how much time passes.

With a prescaler set to TTDR=199 for example, you now have that a single tick for the main timer counter represents a clean 1 μs, thus, to ensure that your timer runs every 10 ms you can set PRD = 10,000! Much simpler!

Lecture notes

This slide answers a question from the block diagram and animation you just saw: why does the CPU timer have two counters in a row instead of one?

The slide starts with the system clock, SYSCLKOUT, at 200 megahertz. One clock period is 1 divided by 200 million, which is 5 nanoseconds. The slide prints 2 nanoseconds, but the tick counts on the slide all use 5 nanoseconds. At that rate, 1 millisecond takes 200,000 clock ticks and 10 milliseconds takes 2,000,000. Those numbers are awkward to compute and easy to get wrong in code.

The solution is to split the job between two counters. The prescaler counter, PSC, reloads from the divide-down register TDDR and controls speed: it sets the unit of time. The main timer counter, TIM, reloads from the period register PRD and controls duration: it sets how many of those units pass before an interrupt. In the slide's words, one counter decides how fast time flows and the other decides how much time passes.

Here is the worked example. The slide writes TTDR, but it means TDDR. Set TDDR = 199. The prescaler then divides by TDDR + 1 = 200, so each tick of the main counter is exactly 1 microsecond. A 10 millisecond period then needs about 10,000 main-counter ticks, so PRD is roughly 10,000.

There is one detail to watch. The counter counts down through zero, so the period is really (PRD + 1) times (TDDR + 1) clock cycles. For exactly 10 milliseconds you set PRD = 9,999. The same plus-one applies to TDDR, which is why 199 gives a divide-by-200.

Quick check: with TDDR = 199, what PRD gives a 1 millisecond interrupt? The answer is 999.

This slide reproduces Figure 3-11 from the TI reference manual, "CPU-Timer Interrupt Signals and Output Signal." A large box on the left is the 28x CPU. Two footnotes say that the timer registers sit on the C28x memory bus, and that the CPU timers are synchronized to SYSCLKOUT, the same 200 MHz clock from the prescaler slide.

The PIE, or Peripheral Interrupt Expansion, is an interrupt router. It takes the many peripheral interrupts and maps them onto CPU interrupt vectors. Timer 0 goes through the PIE because it is commonly used for application-level tasks, and the PIE gives it prioritization and masking.

The software consequence is that using Timer 0 takes four steps. You enable the timer interrupt, enable the PIE group, enable the CPU interrupt, and acknowledge the PIE inside the ISR. This makes Timer 0 ideal for control loops, scheduling and RTOS ticks. A common mistake is forgetting the PIE acknowledge. When you leave it out, the ISR runs once and then never fires again.

Timers 1 and 2 bypass the PIE and use the dedicated CPU interrupts INT13 and INT14. They are intended for high-priority system tasks, real-time services and deterministic timing. They have lower latency, are simpler to configure, and are harder to misuse accidentally.

Each call takes three arguments: which timer to configure, the CPU frequency (200 MHz), and the interrupt period in microseconds. The function does the prescaler and period-register arithmetic from the previous slides for you.

Work out the numbers. 10000 microseconds is 10 ms, so CPU-Timer 0 interrupts at 100 Hz. Timer 1 at 20 ms runs at 50 Hz, and Timer 2 at 40 ms runs at 25 Hz.

The period you pick for a control loop is its sample time. For example, a controller running in a 10 ms timer interrupt uses dt = 0.01 s in its discrete equations.

A common mistake is to treat the third argument as milliseconds. Writing 10 when you mean 10 ms gives a 10 microsecond period, which floods the CPU with interrupts. The unit is microseconds.

Quick check: what value gives a 1 ms control loop? The answer is 1000. You will change these values in lab when you set up your own periodic tasks.
